# 应用角色与权限

应用访问权限可通过两种不可互换的方式授予：

- **角色**：`viewer`、`publisher` 或 `admin`；用户可以持有这三种角色，令牌只能持有前两种。
- **权限**：如 `feedback:read`、`app:publish` 等，可显式授予令牌。

**它们大多控制不同的接口，但在六个反馈接口上有重叠。** 不要仅凭权限名称推断实际能力，请先阅读下一节。

## 容易忽略的区别

**角色控制几乎所有控制台 API。** 发布版本、管理成员和读取构建等操作检查的是角色，而不是权限。

**六个反馈接口是例外。** 它们接受角色或显式权限，因此集成可以读取和回复反馈，而无需拥有同时能够发布版本的 `publisher` 角色：

| 接口 | 接受的角色 | 或接受的权限 |
|---|---|---|
| 列出工单 | `viewer` | `feedback:read` |
| 工单详情 | `viewer` | `feedback:read` |
| 工单附件 | `viewer` | `feedback:read` |
| 实质变更增量流 | `viewer` | `feedback:read` |
| 更新状态或负责人 | `publisher` | `feedback:triage` |
| 发送**公开回复** | `publisher` | `feedback:comment` |
| 发送**内部备注** | `publisher` | `feedback:triage` |

最后两行是同一个接口，通过请求体区分。接口允许持有任一权限的令牌进入，然后针对实际请求的操作再次检查：`feedback:comment` 不能写内部备注，`feedback:triage` 不能回复报告人。**能够访问接口不等于被允许执行其中的每项操作。**

“角色”列不只包括应用角色。这些接口也接受应用所属组织的角色：四个读取接口要求 `viewer`，两个写入接口要求 `member`。因此，**即使没有应用角色或显式权限，也可能通过组织角色访问这些接口**。分析谁可以操作时容易遗漏这条路径，应用成员列表也不会显示它。

**范围由绑定关系决定，而不是权限名称。** 绑定到报告人集成的令牌只能访问该集成的工单，并且会被上表中的控制台接口直接拒绝。未绑定的令牌即使持有同样的 `feedback:read`，也可读取应用的全部工单。权限决定可以做什么，绑定关系决定可对哪些对象执行操作。

**绑定令牌在其集成内没有进一步收窄到单个报告人。** 调用方自行声明代表哪个报告人操作，因此同一个令牌可以回复并关闭该集成拥有的**任何**工单。这个行为由绑定关系决定，同样适用于 `feedback:comment` 及其允许的关闭操作。

## 角色

| 角色 | 预期用途 | 谁可以持有 | 同时包含的权限 |
|---|---|---|---|
| `viewer` | 读取应用数据 | 用户和令牌 | `app:read` |
| `publisher` | CI 和发布自动化 | 用户和令牌 | `app:read`、`app:publish`、`feedback:write` |
| `admin` | 管理应用本身 | **仅用户** | `app:read`、`app:publish`、`app:admin`、`feedback:write` |

角色按上表顺序累积能力。

**不能把 `admin` 作为角色授予令牌。** 签发时会拒绝；该角色只存在于成员关系中，因此管理员级操作需要由用户执行。

这说的是角色，而不是同名权限。令牌仍可显式包含 **`app:admin` 权限范围**，签发会接受它；但当前没有接口接受该权限，所以它不会开放任何操作。

**只授予当前需要的权限范围，不要因为某项权限暂时没有作用就添加它。** 一旦某接口开始接受该权限，它就会立即生效，无需重新签发、重新授权，也不会产生针对该令牌的授权审计事件。这种变化记录在代码和部署历史中，而不是授权历史中；追查令牌何时获得某项能力时应查看部署历史。

**`publisher` 和 `admin` 的有效权限集合包含 `feedback:write`**，因此持有这些角色时不需要另行添加。

**`feedback:triage` 不遵循这一规则。** 没有任何角色包含它，只有显式授予后才能持有；这正是将其与 `publisher` 分开的目的。

以下两个审计问题相似，但答案不同：

- **“谁持有 `feedback:triage`？”** 没有角色包含该权限，因此显式授权列表就是完整答案。
- **“谁可以处理工单？”** 显式授权列表不是完整答案，因为接口也接受角色。仅审计权限会低估可执行操作的主体。

## 权限

**目前只有 `feedback:*` 权限可以单独开放接口。** 上列六个反馈接口是唯一接受权限的接口，其他控制台路由都检查角色。下表中的 `app:*` 名称描述角色携带的权限，也会出现在令牌的有效权限集合中；但**将它单独授予没有角色的令牌，不会开放相应控制台操作**，这些操作需要相应角色。

| 权限 | 含义 | **不授予**的能力 |
|---|---|---|
| `app:read` | 每种角色都包含；对应应用数据读取 | 单独进入控制台；没有接口接受该权限 |
| `app:publish` | `publisher` 和 `admin` 包含；对应构建、版本和分发文件 | 单独进入控制台；修改应用设置或成员 |
| `app:admin` | `admin` 包含；对应设置、成员、凭据和破坏性操作 | 单独进入控制台；操作其他应用 |
| `feedback:write` | 从可信服务端代理**代用户提交工单**；需要绑定报告人集成 | **任何工作人员侧的处理操作。它不是支持或处理权限。** |
| `feedback:read` | 读取工单、详情、附件和实质变更增量流；范围由绑定决定 | 任何写入 |
| `feedback:comment` | 发送报告人可见的**公开回复**；**已绑定**令牌还可**关闭**其集成拥有的工单 | 内部备注、负责人、重新打开或任何其他状态变更 |
| `feedback:triage` | 修改状态和负责人、写**内部备注** | 回复报告人 |
| `feedback:route` | 将不透明路由主体绑定到报告人集成；需要绑定报告人集成 | 读取或写入工单内容 |

`feedback:write` 最容易被误解：它表示服务器可以代用户提交工单，不授予工作人员侧的任何能力。

## 如何计算令牌的访问权限

令牌可以携带角色、权限列表或两者：

    有效访问权限 = 角色包含的权限 ∪ 显式授予的权限

**权限会叠加到角色上，绝不会收窄角色。** 签发一个 `publisher` 令牌并将其“限制”为 `feedback:read`，得到的令牌仍拥有 `publisher` 的全部能力，另加 `feedback:read`。若要将令牌限制为特定权限，应**不授予角色**，只列出所需权限。

还有一条安全规则：若权限列表存在但**为空**，令牌将完全没有访问权限，而不会回退到其角色。不可读取或损坏的授权会以拒绝访问的方式处理。

## 选择授权

- **发布版本的 CI**：使用 `publisher` 角色，不额外添加权限。
- **代用户提交工单的服务器**：不授予角色，授予 `feedback:write`，并**绑定到启用的报告人集成**。未绑定令牌不能签发此权限，因此绑定不可省略。
- **报告人集成**：不授予角色，授予 `feedback:read` 和 `feedback:comment`，并绑定到该集成。注意 `feedback:comment` 还允许它关闭该集成拥有的工单，范围不限于某一报告人。
- **读取并回复反馈的支持自动化**：不授予角色，授予 `feedback:read` 和 `feedback:comment`，不绑定集成。它不能发布、修改状态或写内部备注。
- **内部处理工单的自动化**：不授予角色，授予 `feedback:read` 和 `feedback:triage`。它不能回复报告人。
- **只需查看的用户**：使用 `viewer` 角色。

`feedback:comment` 和 `feedback:triage` 相互独立，没有上下级关系：内部处理工单不意味着可以与客户对话，反之亦然。

应优先选择满足需求的最小授权。对于范围较窄的工作，优先使用显式权限而非角色，因为角色会持续携带其下所有能力，包括未来添加的能力。
