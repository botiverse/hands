# 从服务端或命令行提交反馈

当 Stamp 等产品接收已登录用户或智能体的反馈时，可使用此流程。你的服务端认证调用方、补充产品上下文并提交 Hands 工单。命令行使用自己的产品会话调用该服务端，不需要 Hands 管理员账号。

Hands 令牌和报告人身份必须保密并留在服务端。浏览器和命令行不能提供任意报告人 ID，也不能选择其他用户的 Hands 工单。Hands 负责工单和对话；你的产品负责登录、本地草稿以及向用户投递通知。

## 创建产品应用与集成

为产品创建专用 Hands 应用。网页产品可以使用 `web` 平台，不要将工单提交到其他产品的应用。

应用管理员创建一个启用的报告人集成，以及绑定到该集成、没有应用角色且具有以下权限范围的部署令牌：

- `feedback:write`
- `feedback:read`
- `feedback:comment`
- `feedback:route`

先调用 `POST /api/apps/:appId/reporter-integrations`，然后调用 `POST /api/apps/:appId/deploy-tokens`，传入 `reporter_integration_id` 和这些权限范围，不传 `app_role`。[设置示例](feedback-react.md#one-time-hands-setup)展示了完整请求。将只显示一次的令牌与 Hands 控制台中的应用客户端密钥一起存入服务端密钥管理器。

单独的客户端密钥可以提交反馈，但不能认证报告人以读取工单或接收路由回复。普通应用角色令牌也不能替代仅用于反馈的报告人集成令牌。

## 建立调用方的报告人身份

服务端根据经过认证的主体派生稳定、不透明的报告人 ID，其作用范围限定于 Hands 应用和报告人集成。使用带密钥的 HMAC；如果产品有多个身份提供方，还应包含认证命名空间或服务器以及主体类型。不要使用显示名称或电子邮件地址作为 ID。结果须为 16–200 个 Base64URL 字符。

另行派生用于通知路由的不透明路由主体：`rfr_v1_` 后接 Base64URL 字符。服务端可以维护其到产品用户或智能体的映射，也可以通过确定性方法再次派生。参见[不透明报告人标识派生示例](feedback-react.md#derive-opaque-reporter-coordinates)。

首次提交前，先绑定该主体：

```http
PUT /api/apps/:appId/reporter-feedback/route-subject
Authorization: Bearer <server-side reporter-integration token>
X-Hands-Reporter-Id: <backend-derived reporter id>
Content-Type: application/json

{"route_subject":"rfr_v1_<backend-derived value>"}
```

新绑定返回 `201`；相同绑定返回 `200`；冲突绑定返回 `409`。遇到冲突应停止并解决，不要悄悄将报告人分配到其他目标。可信提交缺少此绑定时返回 `409`，其中 `error: route_required`。

## 提交文本工单

即使只有文本，也要发送 multipart 表单数据：

```http
POST https://hands.build/public/v2/apps/:appSlug/feedback
Authorization: Bearer <server-side reporter-integration token>
X-Hands-Reporter-Id: <backend-derived reporter id>
X-Hands-Client-Key: <app client key>
Content-Type: multipart/form-data; boundary=<generated by the HTTP client>
```

| 表单字段 | 值 |
| --- | --- |
| `message` | 必填文本，1–10,000 个字符。 |
| `kind` | 建议使用 `feedback`，问题使用 `bug`。 |
| `submission_id` | 为本次提交生成一次 UUID，并在重试时保持不变。 |
| `metadata` | 编码为表单字符串的 JSON 对象。 |
| `contact` | 可选联系方式，仅在报告人同意时提供。 |

让 HTTP 客户端的 `FormData` 实现设置 multipart 边界。不要将客户端密钥或 Bearer 令牌放入 URL。

元数据随工单保存。`version_name`、`version_code`（JSON 数字）、`channel` 和 `locale` 等共享字段会填入 Hands 的对应列。产品专用字段应放在带命名空间的对象中，例如：

```json
{
  "version_name": "0.1.0",
  "locale": "en",
  "stamp": {
    "server_id": "<product server id>",
    "principal_type": "agent",
    "error_code": "REPOSITORY_NOT_AUTHORIZED",
    "receipt_id": "<product receipt id>",
    "page_path": "/repositories"
  }
}
```

`stamp` 命名空间是集成约定，而不是特殊的 Hands 模式。服务端应对上下文字段使用允许列表，并在提交前移除访问令牌、Cookie、授权头、私钥以及 URL 中敏感的查询参数。元数据用于描述问题，不能确定工单归属；归属由经过认证的报告人标识决定。

新提交返回 `201`，包含 `id`、`status`、`reference` 和 `idempotent_replay: false`。完全相同的重试返回 `200`、相同工单 ID 和 `idempotent_replay: true`。使用相同提交 ID 但内容或报告人归属不同会返回 `409`。

遇到网络错误、超时或 `429` 时保留草稿，用相同 UUID 和相同内容重试，并遵守 `Retry-After`。不要仅因为响应丢失就生成新 UUID：Hands 可能已经保存工单。如果调用方修改了内容，应将其视为新提交，不要用旧键重试不同载荷。

向用户展示返回的引用或工单 ID，作为支持回执。`ticket_url` 指向 Hands 工作人员控制台，不是报告人查看状态的链接。

## 以报告人身份读取和回复

服务端使用同一个集成令牌和派生的 `X-Hands-Reporter-Id` 执行以下操作：

| 操作 | 接口 |
| --- | --- |
| 列出本人拥有的工单 | `GET /api/apps/:appId/reporter-feedback` |
| 读取工单和公开对话 | `GET /api/apps/:appId/reporter-feedback/:ticketId` |
| 添加回复 | `POST /api/apps/:appId/reporter-feedback/:ticketId/comments` |
| 关闭本人拥有的工单 | `POST /api/apps/:appId/reporter-feedback/:ticketId/close` |

归属检查依据应用、集成和报告人三者的组合。访问其他报告人的工单返回 `404`。提交回复也使用稳定的 `submission_id`；请求体、分页和限制见[接口约定](public-api-reference.md)。内部工作人员评论不会出现在报告人的对话中。

## 通知产品用户或智能体 {#notify-the-products-user-or-agent}

Hands 不会自动向提交者发送 Raft 消息。你可以轮询报告人接口，或为自己的服务端配置签名 Webhook，再通过产品现有的用户或智能体渠道转发通知。

使用具有**应用管理员权限的 Hands 会话**创建 Webhook。应用创建者是应用管理员；此路径不要求组织管理员权限。仅用于反馈的报告人令牌不能执行这些设置操作。

```http
POST /api/apps/:appId/webhooks
Authorization: Bearer <app-admin-session>
Content-Type: application/json

{
  "url": "https://your-product.example/webhooks/hands",
  "secret": "<signing-secret-from-backend-storage>",
  "events": ["feedback:comment_created", "feedback:status_changed"]
}
```

成功的 `201` 响应返回 Webhook `id`、应用范围和 `secret_set: true`，但绝不返回签名密钥。应用由路径中的完整 UUID 选择，不需要在请求体中提供 `app_id`。Hands 命令行也支持创建和列出应用 Webhook。

使用同一个应用管理员会话，通过 `PUT /api/apps/:appId/reporter-integrations/:integrationId/webhooks/:webhookId` 绑定返回的 ID，无需请求体。仅创建 Webhook 不会绑定报告人订阅者。这些订阅与面向工作人员的通用新工单提醒相互独立。

组织路径 `/api/orgs/:orgId/webhooks` 是独立的管理入口，即使请求体包含 `app_id`，也要求**组织管理员**权限。对本集成应使用上面的应用路径，无需请求更广泛的组织权限。

路由前，使用请求的原始字节验证 `X-Hands-Signature`（HMAC-SHA256）。根据稳定的 `X-Hands-Event-Id` 去重；每次投递还包含 `X-Hands-Delivery-Id`。使用已签名载荷中的 `route_subject` 查找接收方。重试复用事件 ID、投递 ID、签名和请求体。请保留轮询以便恢复；Hands 工单是权威记录。

## 集成验收检查

启用入口前：

- 创建产品自己的应用、客户端密钥、报告人集成、令牌和路由绑定，凭据只存于服务端。
- 提交一次并重试完全相同的载荷：应得到一个工单及相同 ID，而不是两个工单。同一 UUID 下修改内容必须返回 `409`。
- 使用两个已认证主体确认跨报告人读取返回 `404`。
- 请求失败或收到 `429` 后保留草稿和相同提交 ID。
- 添加一条工作人员公开回复，确认轮询或签名 Webhook 能送达预期接收者；工作人员内部备注必须保持不可见。

如果需要由现成 React 界面管理草稿、回复状态、附件和重试控制，请参阅 [React 反馈收件箱](feedback-react.md)。原生客户端或命令行也可以不使用 React 而实现同一服务端约定。此服务端代理架构不需要浏览器直接访问 Hands 的 CORS。
